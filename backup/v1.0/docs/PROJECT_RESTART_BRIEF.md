## 一分钟回顾

- **已提交的 Problem Statement**：从完整工作邮件中判断收件人是否需要行动，提出行动和明确的截止时间，并给出支持判断的原文；用户确认后才允许写入日历。完整邮件可能包括主题、正文、历史线程、附件和链接。系统不替用户回复、接受承诺或作业务决定。
- **旧讨论的关键转向**：放弃把单句分类当成整个项目。邮件正文可能只是“请见附件”；行动可能依赖线程上下文。规则是基线，基础模型负责理解和结构化提取；仅在确实需要进一步读取附件或链接时，才考虑有限的工具循环。
- **老师的中期反馈**：肯定同时测 precision 和 recall、运行前固定标准答案、计入正确拒绝、附件作为不可信输入及日历写入前的确认。要求写明自制附件/链接案例数量；评估集定为 **50 例**并列出四类的个数，报告计数；消除 §5 中“自己编排”与“UiPath 低代码编排”的冲突。
- **当前状态**：目录中有提交的 Problem Statement、模板、Watchouts 和 Assessment Timeline，没有课程项目代码或评估集。已提交的形成性文档无法修改，但最终实现和报告可以说明根据反馈作出的调整。

## 建议锁定的边界

| 问题 | 本项目建议决定 | 遇到困难时 |
|---|---|---|
| 系统做什么 | 对一封已取得的邮件及其必要上下文，输出 `requires_action`、行动、明确截止时间或 `null`、证据位置与原文、是否需人工复核 | 多项行动、证据不足或日期含糊时标为需复核，不猜测 |
| 运行形态 | 本地独立原型，用户主动提交/选择邮件，按需处理；结果供人审阅 | 不承诺实时监控、邮箱插件或后台全自动运行 |
| 邮件接入 | 先定义统一输入格式，支持本地 `.eml`/测试夹具；把邮箱 API 放在独立适配层 | Gmail OAuth 接入受阻时，核心系统和评估仍可用本地邮件运行；如做了适配层，展示其接口而不声称已连通真实邮箱 |
| 附件与链接 | 首版只处理受控的纯文本/PDF附件与预先保存的网页内容；展示“需要更多证据→读取→重新判断”的有限工具路径 | 无法安全获取的格式、外部网页或登录页面直接要求人工查看 |
| 外部动作 | 只生成待确认的日历/任务草稿；任何写入都必须经过用户确认 | 若日历 API 未接通，确认后导出 `.ics` 或展示草稿；如实说明没有自动写入 |
| 编排 | **建议选 Python 代码编排**，便于本地复现、记录每次工具调用和跑同一批评估。UiPath 不作为实现依赖 | 最终报告说明：形成性提案提过 UiPath，比较后为控制时间与可复现性改为代码；不要声称试用过而实际没有 |

这样收缩范围不等于忽略真实集成：统一邮件输入格式和独立适配层保留以后接入 Gmail/Outlook 的位置，但 10 月 4 日的核心成果不依赖外部账号授权。Gmail 的完整只读权限属于 restricted scope，公开部署还有授权审核成本；不要把它当作一两天内必然完成的步骤。来源：[Gmail API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)。

## 数据与评估：先固定 50 例，再运行

**候选主来源：**[MAILEX 论文](https://aclanthology.org/2023.emnlp-main.801/)及[作者仓库](https://github.com/salokr/Email-Event-Extraction)。它基于 Enron，含 1,500 个线程、3,936 封邮件及事件/参数标注，比无标签原始邮件更接近任务；作者仓库注明数据集采用 **CC BY-SA 4.0**。但其标签**不是**本项目的“该收件人是否需要行动、行动是什么、截止时间和证据”标准答案，需人工逐例转换和核对；发布改编数据前还需核对原始邮件的隐私与再分发条件。备选是 [CMU Enron 邮件集](https://www.cs.cmu.edu/~enron/)并自行标注；CMU 版本没有附件。[EmailSum](https://github.com/ZhangShiyue/EmailSum)只发布摘要和提取脚本，原始 Avocado 邮件受版权限制，摘要也不是行动标签，因此暂不作为核心评估源。

**拟定分布（总数 50）：**无行动 15；正文明确行动 15；需结合线程/语境判断 10；正文缺关键内容、需读取附件或链接 10（附件 5、链接 5）。前 40 例尽量取自真实邮件并手工标注；后 10 例自行制作、保存生成过程与来源。若 MAILEX 中找不到足够符合定义的前 40 例，应调整来源并公开实际构成，不能硬套标签。四类是刻意平衡的挑战集，不代表真实收件箱患病率/行动比例。

**判定规则先写入标签文件：**“需要行动”指当前收件人被要求做、回复、提交、确认或安排某事；单纯告知某事件、发送者自己将做某事，均不算。只有来源明确给出截止时间才填值；相对时间必须锚定邮件时间和时区。证据应能定位到正文、历史邮件、附件或链接的具体片段；推断性行动可引用多个片段。信息不足时返回 `needs_review`，不编造。多项行动在首版标为人工复核，并记录为范围限制。

**报告实际计数：**TP、FP、FN、TN，precision、recall；无行动的正确拒绝数、证据不足的正确复核数；行动/截止时间/证据各自正确数；附件与链接各自通过数。记录每例输入输出、失败原因、模型版本、token、成本和延迟。标签和判定规则在正式运行前冻结；开发样例与最终 50 例分开，避免看到结果后改答案。

## 实验和实现的最小集合

1. **可运行路径**：输入邮件 → 规则或模型判断 → 校验结构与证据 → 需要时有限读取附件/链接 → 给用户待确认结果。先跑通一例，再扩到 50 例。
2. **必要比较**：简单关键词规则基线 vs 一个基础模型方案，使用同一批 50 例。另对 10 个附件/链接案例比较“只看正文”和“允许读取材料”，报告增益、额外 token/成本和延迟。**暂不训练独立 ML 模型**；老师要求非 AI 基线和合理技术选择，并未要求把规则、ML、LLM、Agent 都各造一个系统。Agent 是多步工具编排方式，不是与 LLM 同层的分类模型。
3. **防错措施**：输出必须符合固定结构；证据片段必须确实出现在已读取的材料中；附件和网页内容只作为数据，不能改变系统指令；含糊则复核；限制附件类型/大小和工具步数。展示漏判、误判和拒绝案例，避免只展示成功演示。
